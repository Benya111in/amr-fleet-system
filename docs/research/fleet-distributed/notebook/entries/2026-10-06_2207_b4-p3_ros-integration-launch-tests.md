## 질문

로봇마다 하나인 `fleet_agent` 노드(투표 코어·장애 감지·CBAA 협상·작업 ID 잠금·복제 WFG 를 묶은 것)를
Gazebo 없이 5 개 띄웠을 때, ① 서버 프로세스를 SIGKILL 해도 `/fleet_p2p/*` 매칭과 구역 배타가 유지되는가,
② 모드가 NORMAL → HOLD_NEW → DEGRADED → (서버 재기동) RESYNC → NORMAL 로 바뀌는가, ③ 낮은 (epoch, leader_id)
명령을 거부하는가, ④ CommEmulator 손실·지연 아래 DEGRADED 협상 할당에서 같은 task_id 의 픽업 시작이 두 번
이상 나오지 않는가.

## 가설과 예측 (결과를 보기 전에 적는다)

근거: 보고서 「분산 플릿 관리 협상 할당과 폴백」 145–158행(모드)·171행 표(메시지)·218–276행(P3 합격),
f1 `protocol.md` 2 절 정족수 교차 논증, f2 TLC(fixB·TaskLock 위반 없음), f3 엄격 모드 216 셀 중복 0 [계산].

- H1 (①): 서버 프로세스 SIGKILL 전후로 `/fleet_p2p/vote`·`/fleet_p2p/beacon`·`/fleet_p2p/neg` 의 발행자·구독자
  수가 에이전트 5 개 그대로다 (서버는 이 토픽에 참여하지 않는다 — 데이터 경로에 중앙 프로세스가 없다).
  한 구역을 5 대가 번갈아 요청·해제하는 동안 모든 표본에서 그 구역 보유 로봇 ≤ 1, kill 뒤에도 허가가 이어진다.
- H2 (②): 마지막 하트비트 뒤 sim 기준 suspect_s(1.5 s) 언저리에 HOLD_NEW, dead_s(5 s) + 비컨 전파 뒤 DEGRADED,
  서버 재기동 뒤 RESYNC, resync_s(시험값) 이상 안정한 뒤 NORMAL. 5 대 모두 이 순서를 지난다.
- H3 (③): 펜스 최댓값보다 낮은 (epoch, leader_id) 의 assign_task 는 거부되고 실행기(가짜)까지 가지 않는다.
  낮은 epoch 의 하트비트는 생존 신호로 세지 않는다 (DEGRADED 가 풀리지 않는다).
- H4 (④): 로봇↔로봇 링크에 손실 0.2 · 지연 U(0, 100) ms 를 수신 측에서 걸어도 픽업 시작 중복 0.
  근거는 "픽업 시작 = 작업 ID 확정 표 과반 ENTER_ACK 뒤에만" 이라는 설계상 참 (f3 의 낙관 모드는 버스트 0.2 에서
  중복 0.1–0.2 % 였다 — 잠금이 없으면 중복이 날 수 있다).
- 가설을 버리는 결과: 어느 표본에서든 같은 구역 보유자 2 대 이상, 매칭 수 감소, 모드 순서 누락, 낮은 epoch 명령
  1 건 이상 수용, 같은 task_id 픽업 시작 2 회 이상. 하나라도 나오면 "미달" 로 적고 원인을 진단한다.

## 해석

- 사전 등록한 네 판정 모두 3/3 통과 — "버리는 결과" 0 건. 가설 H1–H4 를 버리지 않는다.
- 말하는 것: 서버 프로세스가 죽어도 로봇끼리의 토픽 · 투표가 계속되고(데이터 경로에 중앙 프로세스 없음), 한 구역의
  허가가 서로 다른 로봇에게 겹치지 않았으며(87 구간), 낮은 epoch 명령이 실행기에 닿지 않았고, 협상 할당에서 픽업
  중복이 없었다 — **시뮬레이터 없이, 가짜 실행기 · 고정 자세로**.
- 말하지 않는 것: 실제 차체의 동시 점유(제동 · 위치추정 · 별칭)는 범위 밖 (P5). 실제 BT 실행기 · Nav2 · fleet_manager
  원본의 하트비트 경로는 거치지 않았다 (shim). n = 3 이라 "0 건" 은 상한이 크다 (④ 0.10). 손실은 묶음 단위 독립 손실뿐 —
  버스트 · 분할은 loopback 스윕에서 본다.
- ① 의 그래프에 죽은 관찰자의 구독(`/fleet/fleet_heartbeat`)이 kill 3 s 뒤에도 남아 보였다 — DDS 참가자 lease 가
  끝나기 전이다. 발행자(데이터 경로)는 에이전트뿐이었다.
