## 1. CommEmulator (`amr_fleet/comm_emulator.py`, `timer_queue.EmulatedInbox`)

**왜 바꿨나 [코드].** 옛 `LatencyModel` 은 노드마다 `random.Random` 하나였다. fleet_manager 는 모든 로봇의
assign_task 호출이 그 한 열을 나눠 쓰므로, 정책이 호출 순서·횟수를 바꾸면 모든 로봇의 지연열이 밀린다
(보고서 "공통 난수" 문제). 어댑터는 `seed + crc32(robot_id)` 로 로봇마다 열을 달리했지만 링크 개념이 없었다.

**설계.**
- 링크 = (송신자, 수신자). 이름은 `fleet`(중앙), 로봇 id. 설정 규칙의 `src`/`dst` 는 fnmatch 패턴이라
  `amr_* → amr_*` 로 로봇↔로봇 링크를 준다. 위에서부터 처음 맞는 규칙, 없으면 노드 파라미터의 기본 링크
  (`comm_latency_ms` · `drop_rate`, fleet_spawn 의 로봇별 값도 그대로 기본 링크가 된다).
- 메시지 k 의 난수 = `blake2b(시드, src, dst, k)` 의 세 몫(손실 · 지연 · 버스트 손실). 버스트(Gilbert–Elliott)
  상태열 = `blake2b(시드, src, dst, 구간 j)` 로 뽑은 지수 체류 시간 — **sim 시각만의 함수**라 메시지를 몇 개
  보내든 버스트가 오는 시각이 같다 (외생 입력 고정). 분할(대칭 그룹)·단절(한 방향) 일정도 sim 초 구간이다.
- `seed=0` 은 무작위지만 실효 시드를 OS 엔트로피로 하나 뽑아 시작 로그(`comm=… seed=N (무작위로 뽑음)`)에 남긴다.
  **기본 seed 를 0 → 1 로 바꿨다** (보고서 P0 "seed ≠ 0": 쌍 실행이 같은 통신 난수를 공유해야 한다).
  지연 분포·링크 FIFO 는 예전과 같고, 열만 실행마다 같아진다.
- 배선 [코드]: fleet_manager `_dispatch` 가 `transmit('fleet', robot)`, 어댑터 `_on_publish_timer` 가
  `transmit(robot, 'fleet')`. 방송 토픽(비컨·투표)은 송신 측에서 늦추면 모든 수신자가 같은 지연을 받으므로
  수신자마다 `EmulatedInbox.receive(src, msg)` 로 늦추거나 버린다 (송신자별 FIFO, 자기 루프는 바로).
- 설정: 노드 파라미터 `comm_model_file`(YAML, 예시 `config/examples/comm_model.yaml` — F5 부분 분할·상향 단절·
  평균 2.5 s 버스트), 런치 인자 `seed` · `comm_model_file`.

**시험 [시험].** `test_comm_emulator.py` 18 건: 같은 시드 같은 열, **다른 링크에 무작위로 메시지를 끼워 넣어도
이 링크의 열 불변**, 방향성, 골든 값(seed 1 의 fleet→amr_01 k=0..2 = 4.030257 · 88.551425 · 30.899439 ms 고정 —
파생 규칙을 바꾸면 이전 실행을 재현할 수 없다), 손실률 0.25±0.03, 분할·단절, 버스트 비율 0.2±0.06 과
"손실 ⇔ 나쁜 상태", 설정 검증·예시 파일. `test_sim_time.py` 가 EmulatedInbox 를 sim 시각으로 돌린다.

**한계.** 주입 사건은 메모리 이력(`history`, 기본 1000)과 `stats` 뿐이다 — CSV 로그는 다음 물결. 중앙 경로
두 링크(assign_task, robot_state)만 배선했다. traffic/hold 같은 교통 명령에는 걸지 않았다 (지금도 없었다).
DDS RELIABLE 재전송을 흉내 내지 않는다: 유실 = 그 메시지가 앱에 오지 않음.
**버스트 규칙 + 벽시계 노드 시계(use_sim_time=false)는 쓰지 말 것.** 버스트 상태열을 0 초부터 지금까지
펼치므로 첫 송신 비용이 시각에 비례한다 — [측정] now=1e5/1e6/1e7 s 에서 첫 transmit 0.005/0.044/0.448 s,
경계 3 813/37 343/380 309 개 (리뷰 프로브 재실행, `logs/agents/f0b-p0rest/review_fix/burst_probe.log`).
벽시계 epoch(≈1.79e9 s)면 [계산] 약 80 s · 경계 약 6.8e7 개로 노드가 멈춘다. 기본 설정(`comm_model_file` 빈 값)과
Gazebo(sim 시각)에는 해당 없음. 고칠 방향: 시각을 고정 길이 창으로 나눠 창 시작 상태를 정상 분포에서
`blake2b(시드, 링크, 창)` 로 뽑기 (다음 물결).

## 4. 작업 게시판 · 전역 task_id · epoch

**메시지 [코드].** `amr_msgs/Task` 끝에 `uint32 version`, `uint32 epoch`, `string leader_id`, `uint64 seq` 를 더했다.
기본값(0, '')이면 예전과 같다. 영향 범위(grep `amr_msgs`): dashboard `state_store.task_to_dict` 는 필드를 이름으로
나열, evaluation `response_time_logger` 는 status·stamp 만, behavior C++ 는 이름 접근, 통합 시험은 status 상수만 —
**필드 열거·위치 생성자를 쓰는 곳 없음.** 전체 11 패키지 `-Werror` 빌드 경고 0 [시험].

**게시판.** 작업 소스가 `/fleet/task_board`(Task, RELIABLE + TRANSIENT_LOCAL, 깊이 256)에 게시하면 fleet_manager 가
받는다 — 관리자보다 먼저 낸 게시물도 이력으로 받는다 [시험 `test_late_manager_receives_board_history`].
게시물은 전역 task_id 필수(`task_board.make_task_id(source, seq?)` = `<source>.<seq|uuid 64bit>`), status PENDING 만.
세 경로(task_request JSON · task_board · assign_task 서비스)가 `TaskLedger` 하나로 멱등이다 (VDA 5050 규칙):

| 경우 | 처리 |
|---|---|
| 처음 보는 id | 접수 |
| 같은 id · 같은 판 · 같은 내용 | **알림 없이 무시** (예전: 중복은 `fleet/INVALID_TASK`). 서비스 경로는 예전처럼 success=false, message `duplicate` |
| 같은 판 · 다른 내용 / 낮은 판 / 높은 판(갱신) | `fleet/INVALID_TASK` (갱신은 아직 미지원) |

내용 = 픽업·하역 자세(허용오차 1e-6, yaw 는 2π 감김), 물품 유형, 우선순위, 고정 로봇. **마감·접수 시각은 뺀다** —
JSON 상대 마감은 도착 시각마다 절대값이 달라 같은 작업이 두 경로로 오면 어긋난다.

**권위자 표식.** fleet_manager 는 assign_task 요청과 task_events 마다 `(epoch, leader_id, seq)` 를 싣는다.
seq 는 두 경로가 한 카운터를 나눠 쓴다 [시험 `test_nodes_faults.py::test_assign_task_requests_carry_authority_stamp_from_event_counter`
— 가짜 로봇이 받은 요청의 epoch·leader_id, 재전송 때 seq 증가, 접수 알림 < 요청 < 시작 알림 순서, 모듈 전체 seq 유일].
epoch = 파라미터 > `epoch_file`(시작마다 +1, fsync 후 원자적 교체) > 1, leader_id 기본 = 노드 전체 이름.
f1 의 `EpochFence` 키 `(epoch, leader_id)` 와 같은 모양이다.

**한계 (불리한 것).** (1) 받는 쪽 펜싱 없음 — 실행기는 epoch 를 보지 않는다 (P3, f1 `EpochFence` 를 쓰면 된다).
(2) 재기동한 관리자는 게시판 이력으로 **이미 끝난 작업을 다시 접수할 수 있다** — 완료 집합을 로봇에서 모으는
대조(RESYNC)가 없다. 지금은 게시판 발행자가 저장소에 없어 기본 구성에서는 일어나지 않는다. (3) epoch_file 은
관리자 자기 이력만 본다 — 보고서의 "관찰자로 복귀해 로봇들의 max_epoch_seen + 1" 은 P3. (4) 작업 갱신 미지원.

## 5. 결정점 거리 `approach_distance_m` 재계산

요청 거리는 **차체 중심**의 경로 거리다 [코드 `traffic_zones.zone_visits`: 중심점이 다각형에 드는 곳이 입구].
거절되면 차체 앞이 입구에 닿기 전에 서야 하므로

  D = v·(T주기 + T통신 + T실행) + v²/(2a) + e_loc + 여유 + 차체 앞 절반

| 입력 | 값 | 출처 |
|---|---|---|
| v, a | 1.0 m/s, 1.0 m/s² | [코드] `amr_navigation/config/nav2_params.yaml` max_vel_x · decel_lim_x |
| T주기 | 0.5 s | [코드] traffic.yaml `update_rate_hz: 2.0` |
| T통신 | 0.1 s | 명세 최대 통신 지연 (벽시계 값을 sim 으로 줄이지 않음 — 보수적) |
| T실행 | 0.2 s | **[문서주장]** 보고서 가정. BT tick 은 50 Hz 이지만 취소→정지 왕복은 미측정 |
| e_loc, 여유 | 0.05, 0.2 m | [문서주장] 보고서 |
| 차체 앞 절반 | 0.30 m | 0.60 m 차체. **보고서 1.55 m 는 이것을 빠뜨렸다** (노트 (e)는 언급) |

**[계산]** D = 0.8 + 0.5 + 0.05 + 0.2 + 0.30 = **1.85 m** (`decision_distance`, 시험으로 고정). 예전 1.5 m 의 근거
주석 "1.1 m" 는 위치 오차·여유·차체를 뺀 셈이었다. 명세 최고속 2.0 m/s 면 차체 제외 3.85 m (보고서와 같음).

**바꾼 것.** 기본 `approach_distance_m` 2.0 (traffic.yaml · `ZonesConfig`). 그런데 2.0 을 모든 구역에 쓰면 같은 쪽
두 도크 구역(간격 2.0 m)을 `spacing_conflicts` 가 거절해 **traffic_manager 가 시작하지 않는다** (1.64 m 초과면
거절 — [계산] `spacing_conflicts` 를 배포 배치에 돌림). 그래서 구역별 `approach_m` 을 yaml 에 더해 **도크 넷만 1.5 m**
로 두었다. 도크는 결정점 거리에 **미달**이다 — 도크 간격을 넓히거나 두 도크를 한 사슬로 묶어야 한다 (배치 변경).
시험 `test_shipped_approach_meets_decision_distance_except_docks` 가 미달 구역 목록을 도크 넷으로 고정한다.

**부작용 (미측정).** 같은 속도·지연이면 거절된 로봇이 서는 중심 위치가 0.5 m 더 앞(입구에서 먼 쪽)이 된다
(traffic_zones.yaml 주석의 "입구 0.9 ~ 1.5 m 앞" → 1.4 ~ 2.0 m). 랙 끝(입구 1 m 앞)을 지나 주석이 피하려던
**랙 가운데 스테이션 쪽**에 가까워진다. 교차로 사이 4 m 간격에서 대기 자리가
두 구역 밖이라는 성질은 유지된다 (spacing 검사 통과). 시나리오 12 처리량·교착에 미치는 영향은 §6 의 1 회
측정뿐이다.
