## 0. 한 줄 결론 (안 된 것 먼저)

**안 된 것**: 실제 실행기 · BT 에는 아직 붙지 않았다 — 존 BT 노드는 만들고 시험했지만 실행기 등록 표
(`bt_registry.cpp`)와 실행기 런치의 서비스 리매핑, fleet_manager 의 하트비트는 소유 경로 밖이라 요청으로 남겼다
(§7). 그래서 launch 시험의 "서버" 는 원본 fleet_manager_node 와 하트비트를 한 프로세스에 묶은 시험용 shim 이고,
작업 실행은 가짜 실행기다. Gazebo · Nav2 · 실제 자세는 전혀 거치지 않았다 (P5 몫). 교착은 복제 WFG 로 **진단만**
하고 해소 동작은 없다. 운영자 해제 도구는 절차 문서만 있다 (§4.5).

**된 것**: 로봇마다 하나인 `fleet_agent`(순수 코어 + 얇은 노드), 메시지 8 종, 모드 상태기 다섯 모드, 작업 ID 잠금의
실제 결합(투표 코어 task 채널, hold_enter + commit, 확정 뒤 해제 안 함), 에포크 펜스(하트비트 · 중앙 명령 프록시),
존 BT 노드 넷과 서브트리, launch 시험 ①–④. 결과는 §6.

## 1. 구조

```
            /fleet/heartbeat (서버, BEST_EFFORT)      /fleet/task_board (작업 소스, TRANSIENT_LOCAL)
                         │                                        │
  ┌──────────────────────▼────────────────────────────────────────▼───────────────┐
  │ fleet_agent (로봇마다, /amr_0X)                                                 │
  │  node.py  ── 수신 측 CommEmulator(EmulatedInbox) ──┐                            │
  │                                                     ▼                            │
  │  core.py  FleetAgentCore                                                         │
  │   ├ 투표 코어 zone 채널 (ZoneAgent, zone.json)  ← AcquireZoneChain/ZoneGuard/Release│
  │   ├ 투표 코어 task 채널 (ZoneAgent, task.json)  ← VoteTaskLock ← CBAA / 프록시 / BT │
  │   ├ HeartbeatMonitor + LocalHealth + MajoritySuspicion → ModeMachine (modes.py)  │
  │   ├ EpochFence (fence.json) — 하트비트 · assign_task 프록시                      │
  │   ├ CbaaAgent (DEGRADED 에서만, 라운드 0.2 s) + SimExecutor(선택)                │
  │   └ ReplicatedWfg + ProgressConfirmer (진단)                                     │
  └──────────── /fleet_p2p/vote · /fleet_p2p/beacon · /fleet_p2p/neg ────────────────┘
```

- **순수 로직은 rclpy 비의존** (`modes.py`, `task_lock_vote.py`, `sim_exec.py`, `core.py`, `loopback.py`,
  `codec.py`(메시지 모듈만)). 노드(`node.py`)는 콜백을 코어에 넘기고 `drain()` 결과를 발행만 한다.
- **투표 코어를 두 채널로 나눴다.** 한 ZoneAgent 에 구역과 작업 잠금을 섞으면 ① 요청자의 "활성 시도 하나" 때문에
  구역 요청이 이동 중 쥔 작업 잠정 표를 포기시키고, ② 투표자의 "같은 로봇의 더 새 요청 → 옛 잠정 표 회수" 가
  다른 종류의 표를 회수한다. 채널마다 ZoneAgent · 영속 파일 · ReqId 공간이 따로다 (FleetVote.channel).
  f1 코어는 고치지 않고 그대로 두 번 쓴다 — 안전 논증 · 시험이 그대로 적용된다.
- **자기 앞 투표는 DDS 를 거치지 않는다** (노드가 곧바로 다시 넣는다). 남의 앞 투표만 묶음으로 발행한다.
- **영속**: `store_dir/<robot>/{zone,task,fence}.json` (FileStore — 쓰기 → fsync → rename → 디렉터리 fsync).
  f1 리뷰가 짚은 "EpochFence(store) 가 저장소 전체를 덮어써 투표자가 기억 상실이 된다" 위험은 파일을 나눠 피했다.
  `store_dir` 는 파라미터 — 컨테이너에서는 볼륨 경로여야 한다 (재기동에 표가 남아야 이중 투표가 없다).
- **시각**: 노드 시계(use_sim_time 이면 `/clock`) 초 → `Stamp.coerce`. 시각 0(`/clock` 전)에는 기동하지 않는다.

- 투표 묶음 = 한 번의 처리에서 나온 메시지 전부 (수신자마다 걸러 쓴다). 시험의 손실은 수신 측에서 **묶음 단위**로
  건다 — 한 묶음이 한 패킷이다. 내 앞 메시지가 없는 묶음은 링크 모의도 건너뛴다 (난수열이 불필요하게 밀리지 않게).

  최고 epoch 를 읽으려고). 데이터 경로(발행)에는 중앙 프로세스가 없다. SIGKILL 뒤에도 죽은 참가자의 구독이
  그래프에 남아 보인다 (Fast DDS lease 만료 전) — §6 ① 의 `other_sub`.

## 3. 모드 상태기 (`agent/modes.py`)

| base | 조건 | 다음 | 할당 · 구역 |
|---|---|---|---|
| NORMAL | 과반(신선한 비컨 3/5)이 서버 DEAD | DEGRADED | 중앙 할당만 받음(프록시), 작업 잠금은 픽업 직전 확정 |
| NORMAL | 내 감시 SUSPECT/DEAD, 또는 부팅 뒤 unknown_dead_s 동안 무소식 | HOLD_NEW | |
| HOLD_NEW | 과반 DEAD | DEGRADED | 새 작업 보류 (중앙 · 협상 모두), 진행 중 작업 계속 |
| HOLD_NEW | 내 감시 ALIVE | NORMAL | 되돌릴 수 있는 조치만 |
| DEGRADED | 내 감시 ALIVE (펜스 통과 하트비트) | RESYNC | CBAA 협상 + 작업 ID 잠금 |
| RESYNC | 감시가 ALIVE 아님 | DEGRADED | 새 작업 보류 |
| RESYNC | ALIVE 가 resync_s(기본 30 s) 이어지고 서버 ACTIVE · 과반 DEAD 아님 | NORMAL | |

- **ISOLATED 는 덮개다**: 신선한 비컨(자기 포함)이 과반 미만인 상태가 isolate_s 이어지면 effective 모드가 ISOLATED,
  연결이 돌아오면 base 로 복귀. ISOLATED 에서는 새 구역 진입 요청을 거절한다 (어차피 과반 없이는 허가가 안 난다).
- 진실의 원천은 로봇이다: 로봇마다 자기 관측으로 모드를 정한다. 모드는 **효율(할당 방식)만** 바꾼다 — 구역 · 작업
  ID 안전은 정족수가 지고, 오탐해도 안전은 그대로다.
- 관찰자 복귀: 재기동한 서버(shim `--observe-s`)는 ROLE_OBSERVER 하트비트를 내며 비컨의 `fence_epoch` 최댓값을 모아
  `max + 1` 로 정한 뒤에야 fleet_manager_node 를 그 epoch 로 띄우고 ACTIVE 가 된다. 로봇은 OBSERVER 하트비트로
  RESYNC 에 들어가지만 NORMAL 로는 ACTIVE 를 본 뒤에만 간다.
- **찾은 결함 (smoke1, 고침)**: 처음에는 OBSERVER 하트비트도 펜스를 올렸다 → 관찰자는 "로봇이 본 최고 + 1" 을
  후보로 내고 로봇은 그 후보로 펜스를 올려, epoch 가 관찰 2 s 동안 1 → 4 로 되먹임으로 올랐다
  (`/home/CAPYI_AI/runs/b24/b4-p3/smoke1/shim2.log`). 이제 OBSERVER 하트비트는 비교만 하고(`_fence_peek`) 펜스를
  올리지 않는다. 같은 원인의 두 번째 결함: 관찰 → ACTIVE 전환 때 seq 를 1 로 되돌리면 같은 epoch 안의 역행이라
  감시가 버려 DEGRADED 로 떨어졌다 → seq 를 이어 간다. 두 결함 모두 시험으로 고정
  (`test_observer_heartbeat_does_not_raise_the_fence`).

## 4. 실행기 연결

### 4.1 작업 ID 잠금 (`agent/task_lock_vote.py`, 투표 코어 `hold_enter` + `commit`)

f1 · f3 요청대로 f3 의 `TaskLock` 계약을 투표 코어로 구현했다.

| 호출 | 동작 |
|---|---|
| `try_acquire(task)` (CBAA 국소 확정 때) | 처음이면 `task:<id>` 를 **hold_enter** 로 요청 → PENDING. 과반 VOTE(잠정)를 모으면 투표 코어가 VOTED 에서 멈춘다 → **GRANTED = 이동 허가** |
| `commit(task)` (픽업 직전 — 가짜 실행기 또는 BT `CommitTaskLock`) | VOTED → ENTERING 영속화 → ENTER. 과반 ENTER_ACK = HELD = **픽업 허가** |
| `release(task)` | 확정 전이면 요청 포기(잠정 표 회수). **HELD 뒤에는 아무것도 하지 않는다** — 완료 뒤 해제하면 늦게 도착한 옛 낙찰이 끝난 작업을 다시 시작한다 (TLC 반례 `formal/fleet/traces/TL_N3_T1_R2_C0_releaseAfterDone.txt`) |
| DENIED 판정 | 확정 표가 막는다는 NACK(busy) 를 n − q + 1(=3) 투표자에게서 받으면. 단 **내 옛 시도의 RELEASE/ABANDON 을 아직 ACK 하지 않은 투표자의 busy 는 빼고 센다** — 그 busy 는 내 옛 확정 표 탓일 수 있다 (시험 `test_own_unreleased_commit_votes_do_not_count_as_denial`) |

- 투표 코어 변경(`distributed/vote_core.py`): 단계 `VOTED` 추가. VOTED 는 VOTING 과 ENTERING 사이 대기일 뿐이고
  ENTER · ENTER_ACK · HELD 경로와 영속화 순서는 그대로다 → protocol.md §2 의 확정 표 배타 논증이 그대로 적용된다.
  잠정 표 기한은 요청마다 `hold_s` 로 늘릴 수 있다 (이동 시간보다 길게 — 기본 60 s, 활성 파라미터).
- 중복 픽업 0 의 근거는 "픽업 = HELD 뒤에만" 하나다. 잠정 표가 기한으로 풀려 두 로봇이 같은 작업으로 **이동**하는
  일은 생길 수 있지만 둘 다 확정할 수는 없다 (늦은 쪽은 DENIED → 픽업하지 않고 그 작업을 놓는다).
- 한계: NACK 에 보유자 id 가 없어 DENIED 의 보유자를 모른다 (협상 표에는 "막힌 작업" 으로만 표시). DENIED 는
  영구다 — 위 "내 옛 확정 표" 경우를 빼면 확정 표는 풀리지 않으므로 맞지만, 판단이 틀리면 그 로봇은 그 작업을
  다시 잡지 않는다 (다른 로봇은 잡을 수 있다 — 활성만). 작업 잠금은 영원히 남으므로 영속 파일이 작업 수에 비례해
  자란다 (긴 운용에서는 완료 집합 gossip 으로 잘라야 한다 — 다음 단계).

### 4.2 중앙 명령의 에포크 펜스 (실행기 앞 프록시)

`proxy_assign_task:=true` 면 에이전트가 `/<robot>/assign_task` 를 받아 펜스 → 모드 → 작업 잠금 순으로 보고,
통과한 것만 `executor/assign_task` 로 넘긴다. 거부한 명령은 실행기까지 가지 않는다 (§6 ③ 에서 잼).
- 펜스: `(epoch, leader_id)` 사전식 최댓값보다 작으면 거부 (f1 `EpochFence`, 영속). epoch 0 은 옛 구성 호환으로
  펜스 없이 받는다 (`accept_unfenced`, P0 계약 — 끌 수 있다).
- 모드: NORMAL 에서만 받는다 (HOLD_NEW · RESYNC 는 새 작업 보류, DEGRADED 는 협상이 할당).
- 받으면 그 작업의 잠정 잠금(hold)을 시작한다 — 픽업 직전 BT 의 `CommitTaskLock` 이 확정한다.
- 구현 함정 (launch_dev1 에서 찾음, 고침): 비동기 서비스 콜백을 기본(상호 배제) 콜백 그룹에 두면, 실행기 응답을
  기다리는 동안 그룹이 잠겨 응답 콜백과 tick 타이머가 돌지 못하고 노드가 멈춘다. 프록시 서비스 · 클라이언트 ·
  시간 초과 타이머를 재진입 그룹에 둔다.
- **아직 실제 실행기에 걸리지 않았다**: 실행기 서비스 이름을 `executor/assign_task` 로 바꾸는 리매핑이
  `amr_behavior/launch/behavior.launch.py`(소유 밖)에 필요하다 (§7).

### 4.3 구역 사슬 BT 노드 (`amr_behavior/include/amr_behavior/bt_nodes/zone_*.hpp`, 헤더 전용)

| 노드 | 종류 | 동작 |
|---|---|---|
| `AcquireZoneChain zones priority timeout_ms` | StatefulAction | ACQUIRE 를 보내고 사슬 **전부**가 held 일 때 SUCCESS (전부-아니면-전무). 거절(ISOLATED 등) · 시간 초과면 FAILURE, 시간 초과 · halt 면 CANCEL (잠정 표를 풀게). 상태에 요청이 안 보이면 1 s 마다 다시 보냄 (에이전트 쪽 멱등) |
| `ZoneGuard zones` | Condition | 신선한 상태(노드 시계 기준 3 s 이내)의 held 에 전부 있으면 SUCCESS. 상태가 오래되면 FAILURE — ReactiveSequence 안에서 주행을 끊는다 (fail-closed 이중 안전) |
| `ReleaseZones zones` | SyncAction | RELEASE 요청을 보낸다 (실제 RELEASE 는 에이전트의 해제 게이트가 몸체가 밖인지 본 뒤) |
| `CommitTaskLock task_id timeout_ms` | StatefulAction | COMMIT_TASK, `task:<id>` 가 held 면 SUCCESS, denied 면 FAILURE (픽업하지 않는다) |

- 서브트리 `behavior_trees/subtrees/zone_gates.xml`: `ZoneMoveTo`(결정점까지 → AcquireZoneChain →
  ReactiveSequence[ZoneGuard, NavigateToPose] → ReleaseZones), `PickupLocked`(CommitTaskLock). 기본 트리
  (`task_executor.xml`)는 아직 이 파일을 include 하지 않는다.
- 등록: `amr_behavior::registerZoneNodes(factory, params)` 한 줄을 `bt_registry.cpp` 의 ROS 노드 등록 뒤에 넣으면
  된다 (명세 9장 "기존 파일 수정 3 개 이내" 의 경로 A 와 같은 비용). 등록 표는 소유 밖이라 요청으로 남겼다.
- 결정점 · 사슬 계산(`ComputeZoneChain`)은 만들지 않았다 — 서버의 `zone_visits` · `request_chain`(순수 Python)을
  에이전트로 옮겨 사슬을 상태에 실어 주는 것이 다음 단계다. 지금은 BT 가 사슬을 포트로 받는다.

### 4.4 해제 게이트와 재기동 (`release_gate`)

- `zone_map`(설정 기본): RELEASE 는 위치추정이 건강하고 외접 원판(반경 0.36 + 여유 0.1 m)이 구역 다각형과 겹치지
  않을 때만. 판정할 수 없으면(자세 없음 · lost · 다각형 없음) 보류한다. `none`: 곧바로 (시험 · 기하 없음).
- 보고서의 "오도메트리 진행 거리" 조건은 넣지 않았다 — 지금 게이트는 자세 하나에 기댄다 (점대칭 별칭으로 자세가
  튀면 구역 안에서 RELEASE 할 수 있다 → P5 에서 실제 자세 대 믿은 자세를 따로 센다).
- 재기동: 자세를 모르면 디스크의 구역 보유를 모두 남긴다 (`boot(inside=…)`, fail-closed). 남긴 보유는 BT 가 모르는
  **고아**로 따로 들고, 몸체가 밖인 것을 확인하면 푼다. **찾은 결함 (시험, 고침)**: 처음 구현은 자세를 받는 순간
  "판정 끝" 으로 표시해, 그때 몸체가 안에 있으면 나중에 나와도 아무도 풀지 않았다 (영구 점유).
  `test_restart_with_unknown_pose_keeps_zone_until_body_is_seen_outside` 가 고정한다. 작업 잠금은 재기동 때 늘
  모두 남긴다 (완료 뒤에도 풀지 않으므로).

### 4.5 운영자 해제 절차 (문서만 — 도구 미구현)

확정 표는 보유자의 RELEASE 로만 풀린다 (fail-closed). 구역 안에서 로봇이 죽으면 그 구역은 막힌다 — 의도한 거동이다.
1. 로봇이 물리적으로 구역 밖인지 사람이 확인한다 (치우거나 밀어낸다).
2. 그 로봇의 에이전트를 저장소 그대로 다시 띄운다 (`release_gate:=zone_map`, 위치추정이 잡히면 고아 보유를 스스로 푼다).
3. 저장소가 손상돼 기억 상실이면 그 로봇은 자기 요청 ID 를 모른다 → 각 투표자의 `zone.json` 의 확정 표
   `votes[<자원>].req` 가 그 요청 ID 다. 그 ID 로 RELEASE 를 투표자 전원에게 보내는 운영자 도구가 필요하다 (**미구현**).
   손상된 투표자는 영구 기권하므로 5 대 중 1 대까지는 과반이 남는다.

## 5. 교착 (진단만)

비컨에 out-edge 를 싣고(내 구역 요청 ∩ 남의 held → `token` 간선) 모두가 같은 `ReplicatedWfg` · Tarjan ·
`ProgressConfirmer`(진행량을 모르면 확인 창만으로) · timestamp 희생자를 계산해 상태의 `deadlock_members` ·
`deadlock_victim` 에 싣는다. 희생자의 양보 동작(BT YIELD · 재계획)은 없다 — P5 이후.
