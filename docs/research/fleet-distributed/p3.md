  └──────────── /fleet_p2p/vote · /fleet_p2p/beacon · /fleet_p2p/neg ────────────────┘

- **순수 로직은 rclpy 비의존** (`modes.py`, `task_lock_vote.py`, `sim_exec.py`, `core.py`, `loopback.py`,
  `codec.py`(메시지 모듈만)). 노드(`node.py`)는 콜백을 코어에 넘기고 `drain()` 결과를 발행만 한다.
- **투표 코어를 두 채널로 나눴다.** 한 ZoneAgent 에 구역과 작업 잠금을 섞으면 ① 요청자의 "활성 시도 하나" 때문에
  구역 요청이 이동 중 쥔 작업 잠정 표를 포기시키고, ② 투표자의 "같은 로봇의 더 새 요청 → 옛 잠정 표 회수" 가
  다른 종류의 표를 회수한다. 채널마다 ZoneAgent · 영속 파일 · ReqId 공간이 따로다 (FleetVote.channel).
  f1 코어는 고치지 않고 그대로 두 번 쓴다 — 안전 논증 · 시험이 그대로 적용된다.
- **자기 앞 투표는 DDS 를 거치지 않는다** (노드가 곧바로 다시 넣는다). 남의 앞 투표만 묶음으로 발행한다.
- **영속**: `store_dir/<robot>/{zone,task,fence}.json` (FileStore — 쓰기 → fsync → rename → 디렉터리 fsync).
  f1 리뷰가 짚은 "EpochFence(store) 가 저장소 전체를 덮어써 투표자가 기억 상실이 된다" 위험은 파일을 나눠 피했다.
  `store_dir` 는 파라미터 — 컨테이너에서는 볼륨 경로여야 한다 (재기동에 표가 남아야 이중 투표가 없다).
- **시각**: 노드 시계(use_sim_time 이면 `/clock`) 초 → `Stamp.coerce`. 시각 0(`/clock` 전)에는 기동하지 않는다.

## 3. 모드 상태기 (`agent/modes.py`)

| base | 조건 | 다음 | 할당 · 구역 |
|---|---|---|---|
| NORMAL | 과반(신선한 비컨 3/5)이 서버 DEAD | DEGRADED | 중앙 할당만 받음(프록시), 작업 잠금은 픽업 직전 확정 |
| NORMAL | 내 감시 SUSPECT/DEAD, 또는 부팅 뒤 unknown_dead_s 동안 무소식 | HOLD_NEW | |
| HOLD_NEW | 과반 DEAD | DEGRADED | 새 작업 보류 (중앙 · 협상 모두), 진행 중 작업 계속 |
| HOLD_NEW | 내 감시 ALIVE | NORMAL | 되돌릴 수 있는 조치만 |
| DEGRADED | 내 감시 ALIVE (펜스 통과 하트비트) | RESYNC | CBAA 협상 + 작업 ID 잠금 |
| RESYNC | 감시가 ALIVE 아님 | DEGRADED | 새 작업 보류 |
| RESYNC | ALIVE 가 resync_s(기본 30 s) 이어지고 서버 ACTIVE · 과반 DEAD 아님 | NORMAL | |

- **ISOLATED 는 덮개다**: 신선한 비컨(자기 포함)이 과반 미만인 상태가 isolate_s 이어지면 effective 모드가 ISOLATED,
  연결이 돌아오면 base 로 복귀. ISOLATED 에서는 새 구역 진입 요청을 거절한다 (어차피 과반 없이는 허가가 안 난다).
- 진실의 원천은 로봇이다: 로봇마다 자기 관측으로 모드를 정한다. 모드는 **효율(할당 방식)만** 바꾼다 — 구역 · 작업
  ID 안전은 정족수가 지고, 오탐해도 안전은 그대로다.
- 관찰자 복귀: 재기동한 서버(shim `--observe-s`)는 ROLE_OBSERVER 하트비트를 내며 비컨의 `fence_epoch` 최댓값을 모아
  `max + 1` 로 정한 뒤에야 fleet_manager_node 를 그 epoch 로 띄우고 ACTIVE 가 된다. 로봇은 OBSERVER 하트비트로
  RESYNC 에 들어가지만 NORMAL 로는 ACTIVE 를 본 뒤에만 간다.
- **찾은 결함 (smoke1, 고침)**: 처음에는 OBSERVER 하트비트도 펜스를 올렸다 → 관찰자는 "로봇이 본 최고 + 1" 을
  후보로 내고 로봇은 그 후보로 펜스를 올려, epoch 가 관찰 2 s 동안 1 → 4 로 되먹임으로 올랐다
  (`/home/CAPYI_AI/runs/b24/b4-p3/smoke1/shim2.log`). 이제 OBSERVER 하트비트는 비교만 하고(`_fence_peek`) 펜스를
  올리지 않는다. 같은 원인의 두 번째 결함: 관찰 → ACTIVE 전환 때 seq 를 1 로 되돌리면 같은 epoch 안의 역행이라
  감시가 버려 DEGRADED 로 떨어졌다 → seq 를 이어 간다. 두 결함 모두 시험으로 고정
  (`test_observer_heartbeat_does_not_raise_the_fence`).

## 4. 실행기 연결

### 4.1 작업 ID 잠금 (`agent/task_lock_vote.py`, 투표 코어 `hold_enter` + `commit`)

f1 · f3 요청대로 f3 의 `TaskLock` 계약을 투표 코어로 구현했다.

| 호출 | 동작 |
|---|---|
| `try_acquire(task)` (CBAA 국소 확정 때) | 처음이면 `task:<id>` 를 **hold_enter** 로 요청 → PENDING. 과반 VOTE(잠정)를 모으면 투표 코어가 VOTED 에서 멈춘다 → **GRANTED = 이동 허가** |
| `commit(task)` (픽업 직전 — 가짜 실행기 또는 BT `CommitTaskLock`) | VOTED → ENTERING 영속화 → ENTER. 과반 ENTER_ACK = HELD = **픽업 허가** |
| `release(task)` | 확정 전이면 요청 포기(잠정 표 회수). **HELD 뒤에는 아무것도 하지 않는다** — 완료 뒤 해제하면 늦게 도착한 옛 낙찰이 끝난 작업을 다시 시작한다 (TLC 반례 `formal/fleet/traces/TL_N3_T1_R2_C0_releaseAfterDone.txt`) |
| DENIED 판정 | 확정 표가 막는다는 NACK(busy) 를 n − q + 1(=3) 투표자에게서 받으면. 단 **내 옛 시도의 RELEASE/ABANDON 을 아직 ACK 하지 않은 투표자의 busy 는 빼고 센다** — 그 busy 는 내 옛 확정 표 탓일 수 있다 (시험 `test_own_unreleased_commit_votes_do_not_count_as_denial`) |

- 투표 코어 변경(`distributed/vote_core.py`): 단계 `VOTED` 추가. VOTED 는 VOTING 과 ENTERING 사이 대기일 뿐이고
  ENTER · ENTER_ACK · HELD 경로와 영속화 순서는 그대로다 → protocol.md §2 의 확정 표 배타 논증이 그대로 적용된다.
  잠정 표 기한은 요청마다 `hold_s` 로 늘릴 수 있다 (이동 시간보다 길게 — 기본 60 s, 활성 파라미터).
- 중복 픽업 0 의 근거는 "픽업 = HELD 뒤에만" 하나다. 잠정 표가 기한으로 풀려 두 로봇이 같은 작업으로 **이동**하는
  일은 생길 수 있지만 둘 다 확정할 수는 없다 (늦은 쪽은 DENIED → 픽업하지 않고 그 작업을 놓는다).
- 한계: NACK 에 보유자 id 가 없어 DENIED 의 보유자를 모른다 (협상 표에는 "막힌 작업" 으로만 표시). DENIED 는
  영구다 — 위 "내 옛 확정 표" 경우를 빼면 확정 표는 풀리지 않으므로 맞지만, 판단이 틀리면 그 로봇은 그 작업을
  다시 잡지 않는다 (다른 로봇은 잡을 수 있다 — 활성만). 작업 잠금은 영원히 남으므로 영속 파일이 작업 수에 비례해
  자란다 (긴 운용에서는 완료 집합 gossip 으로 잘라야 한다 — 다음 단계).

### 4.2 중앙 명령의 에포크 펜스 (실행기 앞 프록시)

`proxy_assign_task:=true` 면 에이전트가 `/<robot>/assign_task` 를 받아 펜스 → 모드 → 작업 잠금 순으로 **검사만** 하고,
통과한 것만 `executor/assign_task` 로 넘긴다. 거부한 명령은 실행기까지 가지 않는다 (§6 ③ 에서 잼).
- 펜스: `(epoch, leader_id)` 사전식 최댓값보다 작으면 거부 (f1 `EpochFence`, 영속). epoch 0(옛 구성)은 **펜스가
  생기기 전에만** 받는다 (`accept_unfenced`). 리뷰 전에는 펜스 최댓값과 무관하게 통과했다 (리뷰 비차단 지적, 고침).
- 모드: NORMAL 에서만 받는다 (HOLD_NEW · RESYNC 는 새 작업 보류, DEGRADED 는 협상이 할당).
- 작업 잠금 검사: 그 작업을 남이 **확정**했으면 거부 — `taken`(비컨 held 의 `task:*`, picked_up 인 current_task_id,
  내 픽업 시작, 재기동 때 남긴 확정) 또는 DENIED. 남이 **잠정**으로 쫓는 작업(비컨 current_task_id, 픽업 전)은
  `peer_pursuing()` — 신선한 비컨(받은 뒤 ≤ beacon_ttl_s)에서 매번 다시 계산하는 일시 집합 — 이고, CBAA 후보에서만 뺀다.
  중앙 할당은 그것으로 거부하지 않는다: 관리자는 거부를 받으면 곧바로 다음 로봇에 준다(`fleet_manager_node.py`
  `_abort_dispatch`) — 옛 비컨이 남은 동안 로봇들이 연달아 거부해 모두 backoff 에 빠진다. 둘이 쫓아도 확정은 잠금이
  하나로 막는다 (§6 ④b).
- **잠정 잠금은 실행기가 받은 뒤에 시작한다** (`on_central_result`, 리뷰 반영):

| 실행기 결과 | 에이전트 |
|---|---|
| 수락 | hold(잠정 잠금) + central_task. 종료 보고를 놓친 이전 중앙 작업이 남아 있으면 그 확정 전 시도를 놓고 바꾼다 |
| 거부(`success=false`) · 실행기 없음 | 아무것도 잡지 않는다 (사건 `central_rejected`). 같은 작업이 이미 중앙 작업이면 그대로 — 실행기가 그 작업 중이라 `busy:<id>` 로 거부한 것 |
| 시간 초과 | 결과를 모른다 — 받았다고 보고 hold (관리자도 robot_state 로 확인할 때까지 재할당을 미룬다). 다른 중앙 작업이 진행 중이면 덮지 않는다 |
| 응답보다 그 작업의 종료(task_status) 가 먼저 | 잡지 않는다 — 작업별 종료 보고 수를 넘길 때 받아 둔 값(token)과 비교 |

- 리뷰의 고칠 방향("먼저 잡고 확정 거부 때 놓는다")을 그대로 쓰지 않은 이유: 실행기는 작업 중이면 `busy:<id>` 로
  거부한다(`executor_context.cpp` evaluateTask). 먼저 잡으면 바쁜 로봇에 온 새 작업 B 의 hold 가 진행 중 작업 A 의
  잠정 시도를 이미 포기시키고(`vote_core.request` 는 진행 중 시도를 포기) central_task 를 B 로 덮은 뒤라 거부 뒤
  되돌릴 수 없다. 결과(거부 뒤 남는 것 없음)는 같고 덮어쓰기가 없다.
- 중앙 작업이 끝나면(task_status COMPLETED/FAILED) 확정 전 잠금을 놓는다. 확정(HELD) 뒤에는 놓지 않는다.
- **리뷰가 찾은 결함 (고침)**: 리뷰 전에는 프록시가 실행기 응답 전에 hold · central_task 를 잡고 거부 · 무응답 뒤에도
  놓지 않았고, 비컨 current_task_id 를 단조 `taken` 에 넣었다. 그래서 실행기가 거부했거나 픽업 전에 FAILED 로 끝난
  작업을 관리자가 다른 로봇에 다시 주면 그 로봇의 프록시가 `task_taken` 으로 계속 거부했다 (리뷰 탐침 P1: 강제 commit 도
  150 s 동안 HELD 안 됨, P1b: 4/5 로봇의 taken 에 남음). 개발 중 고친 "중앙 작업 종료 뒤 남는 잠금 요청"(`7db1beb`)은
  같은 로봇의 COMPLETED/FAILED 경로만 고친 것이었다. 회귀 시험: `test_executor_rejection_lets_another_robot_take_the_task`,
  `test_failed_before_pickup_lets_another_robot_take_the_task`, `test_central_result_rules`,
  `test_peer_pursuit_is_transient_but_confirmed_tasks_are_permanent`, launch ④b.
- **남은 위험 (시간 초과 경로, §8)**: 시간 초과 뒤 실행기가 실제로는 받지 않았으면 잠정 잠금이 다음 중앙 수락(교체)
  전까지 남아 hold_s 마다 다시 잡힌다. 관리자가 그 작업을 다른 로봇에 주면 그 로봇의 확정이 늦어진다 — 리뷰 P1 과 같은 꼴이
  시간 초과 경로에만 남는다 (리뷰도 "결과를 모르므로 둔다" 로 권했다).
- 구현 함정 (launch_dev1 에서 찾음, 고침): 비동기 서비스 콜백을 기본(상호 배제) 콜백 그룹에 두면, 실행기 응답을
  기다리는 동안 그룹이 잠겨 응답 콜백과 tick 타이머가 돌지 못하고 노드가 멈춘다. 프록시 서비스 · 클라이언트 ·
  시간 초과 타이머를 재진입 그룹에 둔다.
- **아직 실제 실행기에 걸리지 않았다**: 실행기 서비스 이름을 `executor/assign_task` 로 바꾸는 리매핑이
  `amr_behavior/launch/behavior.launch.py`(소유 밖)에 필요하다 (§7).

### 4.3 구역 사슬 BT 노드 (`amr_behavior/include/amr_behavior/bt_nodes/zone_*.hpp`, 헤더 전용)

| 노드 | 종류 | 동작 |
|---|---|---|
| `AcquireZoneChain zones priority timeout_ms` | StatefulAction | ACQUIRE 를 보내고 사슬 **전부**가 held 일 때 SUCCESS (전부-아니면-전무). 거절(ISOLATED 등) · 시간 초과면 FAILURE, 시간 초과 · halt 면 CANCEL (잠정 표를 풀게). 상태에 요청이 안 보이면 1 s 마다 다시 보냄 (에이전트 쪽 멱등) |
| `ZoneGuard zones` | Condition | 신선한 상태(노드 시계 기준 3 s 이내)의 held 에 전부 있으면 SUCCESS. 상태가 오래되면 FAILURE — ReactiveSequence 안에서 주행을 끊는다 (fail-closed 이중 안전) |
| `ReleaseZones zones` | SyncAction | RELEASE 요청을 보낸다 (실제 RELEASE 는 에이전트의 해제 게이트가 몸체가 밖인지 본 뒤) |
| `CommitTaskLock task_id timeout_ms` | StatefulAction | COMMIT_TASK, `task:<id>` 가 held 면 SUCCESS, denied 면 FAILURE (픽업하지 않는다) |

  (`task_executor.xml`)는 아직 이 파일을 include 하지 않는다.
- 등록: `amr_behavior::registerZoneNodes(factory, params)` 한 줄을 `bt_registry.cpp` 의 ROS 노드 등록 뒤에 넣으면
  된다 (명세 9장 "기존 파일 수정 3 개 이내" 의 경로 A 와 같은 비용). 등록 표는 소유 밖이라 요청으로 남겼다.
- 결정점 · 사슬 계산(`ComputeZoneChain`)은 만들지 않았다 — 서버의 `zone_visits` · `request_chain`(순수 Python)을
  에이전트로 옮겨 사슬을 상태에 실어 주는 것이 다음 단계다. 지금은 BT 가 사슬을 포트로 받는다.

### 4.4 해제 게이트와 재기동 (`release_gate`)

- `zone_map`(설정 기본): RELEASE 는 위치추정이 건강하고 외접 원판(반경 0.36 + 여유 0.1 m)이 구역 다각형과 겹치지
  않을 때만. 판정할 수 없으면(자세 없음 · lost · 다각형 없음) 보류한다. `none`: 곧바로 (시험 · 기하 없음).
- 보고서의 "오도메트리 진행 거리" 조건은 넣지 않았다 — 지금 게이트는 자세 하나에 기댄다 (점대칭 별칭으로 자세가
  튀면 구역 안에서 RELEASE 할 수 있다 → P5 에서 실제 자세 대 믿은 자세를 따로 센다).
- 재기동: 자세를 모르면 디스크의 구역 보유를 모두 남긴다 (`boot(inside=…)`, fail-closed). 남긴 보유는 BT 가 모르는
  **고아**로 따로 들고, 몸체가 밖인 것을 확인하면 푼다. **찾은 결함 (시험, 고침)**: 처음 구현은 자세를 받는 순간
  "판정 끝" 으로 표시해, 그때 몸체가 안에 있으면 나중에 나와도 아무도 풀지 않았다 (영구 점유).
  `test_restart_with_unknown_pose_keeps_zone_until_body_is_seen_outside` 가 고정한다. 작업 잠금은 재기동 때 늘
  모두 남긴다 (완료 뒤에도 풀지 않으므로).

### 4.5 운영자 해제 절차 (문서만 — 도구 미구현)

확정 표는 보유자의 RELEASE 로만 풀린다 (fail-closed). 구역 안에서 로봇이 죽으면 그 구역은 막힌다 — 의도한 거동이다.
1. 로봇이 물리적으로 구역 밖인지 사람이 확인한다 (치우거나 밀어낸다).
2. 그 로봇의 에이전트를 저장소 그대로 다시 띄운다 (`release_gate:=zone_map`, 위치추정이 잡히면 고아 보유를 스스로 푼다).
3. 저장소가 손상돼 기억 상실이면 그 로봇은 자기 요청 ID 를 모른다 → 각 투표자의 `zone.json` 의 확정 표
   `votes[<자원>].req` 가 그 요청 ID 다. 그 ID 로 RELEASE 를 투표자 전원에게 보내는 운영자 도구가 필요하다 (**미구현**).
   손상된 투표자는 영구 기권하므로 5 대 중 1 대까지는 과반이 남는다.

   기다린다) 영속 상태가 해제마다 자란다. 로봇 고장 시나리오(F6)에서 재전송 수 · 파일 크기를 재고, 필요하면 투표자별
   지수 백오프 + 재기동 동기화를 넣는다. 묘비 상한(256) 밖의 아주 늦은 중복도 같은 범주(활성만).
10. 작업 잠금 영속 파일은 작업 수에 비례해 자란다 (확정 잠금을 풀지 않으므로) — 긴 운용에서는 완료 집합 gossip 으로 자를 것.
11. (리뷰 반영에서 남긴 것) 프록시 **시간 초과** 경로: 결과를 모르므로 hold 한다 — 실행기가 실제로는 받지 않았으면
    잠정 잠금이 다음 중앙 수락 전까지 남아 hold_s(60 s)마다 다시 잡힌다. 관리자가 그 작업을 다른 로봇에 주면 그 로봇의
    확정이 늦어진다. 실행기의 task_status IN_PROGRESS(수락 때 발행)로 확인하고 일정 시간 안에 안 오면 놓는 규칙이 후보 —
    IN_PROGRESS 가 응답보다 먼저 와 버려지는 경합을 같이 다뤄야 한다 (token 처럼 작업별 수로).
12. (④c 관찰) **분할 전 VOTED 였던 작업 잠금 시도는 분할 중 확정을 못 한다** — ENTER 는 표를 준 투표자에게만 가므로,
    표를 준 투표자 일부가 건너편이면 다수 쪽 로봇도 HELD 를 못 받고, 시도 기한(task_hold_s 60 s)이 실행기
    commit_timeout(시험 25 s)보다 길어 다시 모으지 못한 채 실패한다 (§6.3 ④c 의 다수 쪽 commit_timeout). 안전 문제는 아니고
    활성 비용. ENTERING 에 짧은 하위 기한(ENTER_ACK 를 못 모으면 ABANDON 후 다시 VOTING)을 두는 것이 후보 — 투표 코어
    프로토콜 변경이라 f2 모델(QuorumVote)과 같이 다시 검사해야 한다.
13. (리뷰 비차단, 미수정) `ZoneAgentLink::freshState` 는 age < 0(미래 stamp)을 신선하다고 본다 — sim 리셋 · 시계 혼용 때
    fail-open. 프로세스마다 /clock 수신 시각이 조금 달라 작은 음수는 정상이므로 "−0.5 s 이상만 신선" 같은 허용치가 맞다.
14. (리뷰 비차단) BT 존 노드의 시간 초과(`timeout_ms`)는 벽시계(steady)이고 에이전트 · 상태 신선도는 sim 시각이다.
    RTF 0.25 면 CommitTaskLock 30 s(벽시계)는 sim 7.5 s 라, 투표 재시도 · 백오프(sim)보다 먼저 끝나 픽업 실패가 늘 수 있다.
    P5 에서 RTF 별로 CommitTaskLock 실패율을 재고, 필요하면 노드 시계(sim)로 바꾼다.
15. ISOLATED 는 launch 수준에서 시험하지 않았다 (loopback `test_isolated_robot_refuses_new_entry_and_others_continue` 만).
    ④c 의 소수 쪽이 분할 중 ISOLATED 로 가지만 판정하지 않는다.

### 10.1 구역 사슬: 에이전트 경로 게이트 (ZoneMoveTo 대신, `b2b8e2c`)

p3 §7 요청은 "교차로 사슬은 ZoneMoveTo" 였지만 ZoneMoveTo 는 결정점 · 사슬을 포트로 받는다 — 실제 주행에서는 Nav2 가 경로를
정하기 전에는 사슬을 모르고, 경로 하나가 사슬 여럿을 지난다 (`ComputeZoneChain` 은 P3 에서 "다음 단계" 로 남았다). 그래서
보고서의 두 장치 중 **"이중 안전" 쪽(진입선까지 거리가 결정점보다 짧은데 허가가 없으면 goal 취소 · 정지)** 을 주 장치로 쓰고,
사슬 계산은 에이전트가 로봇의 `plan` 으로 한다 (`agent/path_gate.py`, rclpy 비의존):

| 단계 | 규칙 | 근거 |
|---|---|---|
| 사슬 | 서버 traffic_manager 와 같은 `zone_visits` · `request_chain` (같은 traffic_zones.yaml · traffic.yaml 값) | 서버 코드를 로봇 쪽으로 옮긴다 (보고서) |
| 사전 요청 | 첫 미진입 구역 입구가 요청 거리 + `path_gate.prerequest_m`(1.0 m) 안이면 사슬 전체를 투표로 요청 | 투표 왕복 동안 멈추지 않게 ("결정점에 다가가는 동안 미리 요청") |
| 정지 | 사슬 첫 입구가 요청 거리(결정점, 교차로 · 도크 2.0 · 통로 2.5 m) 안인데 사슬 전부를 쥐지 못하면 그 구역을 상태 `requested` 에 싣는다 → BT `ZonePathClear` FAILURE → TrafficGate RUNNING → 주행 goal 취소 | 전부-아니면-전무 (첫 구역만 쥐고 그 안에서 서지 않게) |
| 구역 안에서 기다리지 않기 | 몸체가 구역 k 에 걸쳐 있으면 k 와 묶이지 않은 다음 구역은 k 를 나온 뒤 요청 | `request_chain` 의 occupied 규칙 그대로 |
| 취소 · 해제 | 사슬이 필요 없어지면(경로 바뀜 · 도착 · 멈추는 단계) 진행 중 요청 취소. 보유 구역이 사슬 · 남은 경로 · 몸체 밖이면 해제 후보 → `zone_map` 해제 게이트(위치추정 건강 + 원판 0.46 m 가 다각형 밖)가 RELEASE | P3 해제 게이트 그대로 |
| 단계 | `executor/phase` 가 MOVING · RETURNING · RECOVERING 일 때만 plan 을 본다 (도킹 · 적재 · 대기의 plan 은 지난 주행 것). 단계를 모르면 본다 | |
| fail-closed | 움직이는 단계인데 자세를 모르면 `zone:?pose` 로 막는다. 에이전트 상태가 3 s 넘게 오래되면 `ZonePathClear` 가 막는다 | 무응답 = 미허가 |

- `requested` 의 뜻이 바뀐다 — 경로 게이트를 켜면 "지금 허가가 있어야 움직일 수 있는 미보유 구역" (P3 의 "진행 중 투표 요청" 이
  아니다. msg 주석은 amr_msgs 소유 밖이라 그대로). 켜면 구역 요청은 게이트가 쥐므로 BT 의 명시 ACQUIRE(ZoneMoveTo)와 함께 쓰지 않는다.
- 분산 TrafficGate (`subtrees/yield_distributed.xml`) 순서: **구역 게이트 먼저**, 그다음 중앙 hold. 그래서 양보 이동(포켓 주행)도
  구역 허가 없이 구역에 들어가지 않는다. 중앙 hold 는 `IsFleetServerAlive` 일 때만 따른다 (분산 모드에서 hold 는 권고 —
  latched 값이 서버 사망 뒤 남아 영영 서지 않게). 교통 관리자는 분산 모드에서 구역 토큰을 끈다 (`zones.tokens false` — 둘 다
  켜면 중앙은 A 에게, 정족수는 B 에게 같은 구역을 줘 서로 막는다). 교차 예측 · 교착 해소는 그대로다.
- 남은 위험: 새 주행의 첫 plan 이 오기 전(≤ 1 s)에는 지난 plan 으로 판단한다 — 출발점에서 1 m 안의 구역이면 늦을 수 있다 (중앙
  traffic_manager 도 같은 /plan 에 기댄다). 경로가 바뀌어 첫 구역만 쥔 채 다음 구역을 기다리면(사슬이 길어진 경우) 그 앞에서
  쥔 채 선다 — 교착 후보 (복제 WFG 진단만). Nav2 실제 제동 · 위치추정 오차에서 결정점 정지가 구역 밖인지는 Gazebo 몫 (§10.6).

### 10.2 협상 낙찰 → 실제 실행기, 낡은 LOCKED 정리 (`b2b8e2c`)

- 가짜 실행기(sim_execution)가 없으면 CBAA 낙찰(잠정 과반 GRANTED)을 `dispatch` 로 내고 노드가 `executor/assign_task` 로
  게시판의 작업을 넘긴다. 실행기 BT 의 `PickupLocked` 가 픽업 직전 확정하고(HELD 뒤에만 적재), `task_status` 로 끝을 받는다.
  거부면 잠정 잠금을 놓고 낙찰을 버린다 — 사유가 busy 면 그 작업을 막지 않는다(실행기가 비면 다시 입찰). 실행기가 IDLE 이 아니거나
  중앙 작업 중이면 입찰하지 않는다 (가짜 실행기 경로는 P3 그대로).
- **P3 결함 (찾음, 고침 — 켜고 끌 수 있게)**: CBAA 는 잠정 과반에서 LOCKED 를 알리고 병합 규칙이 "잠금은 사실 — 늘 받아들인다"
  라, 낙찰 로봇이 **픽업 전에** 실패해 놓으면(주행 실패 · 확정 시간 초과 · 실행기 거부) 남은 그 작업을 영영 다시 잡지 못했다
  (`test_agent_dispatch.py::test_failure_before_pickup_lets_another_robot_take_it[False]` 가 그 결함을 대조군으로 고정한다 —
  DEGRADED 동안 작업 미완). 실제 실행기에서는 픽업 전 실패가 흔하다. `nego.stale_lock_gc`(노드 기본 true, 코어 기본 false — P3
  loopback 스윕은 그대로): 보유자의 **신선한** 비컨이 1 s 동안 "그 작업을 쫓지도 쥐지도 않음" 이면 내 표에서 지우고, 동료의 옛
  메시지가 되돌려 놓아도 같은 조건이면 곧바로 다시 지운다. 비컨이 없거나 오래되면(분할 · 사망) 지우지 않는다. 안전은 작업 ID
  잠금(정족수)이 진다 — 지운 뒤 두 로봇이 같은 작업으로 **이동**할 수는 있어도 확정은 하나뿐이다.
- **이 정리의 거짓 양성 (내 결함, 찾음 · 고침 `f618e59`)**: 처음 판(`b2b8e2c`)은 "신선한 비컨이 1 s 동안 안 쫓음" 만 보았다.
  보유자가 낙찰하는 틱의 비컨은 협상 앞에서 만들어져 현재 작업이 없고, 손실 0.2 에서 그 뒤 비컨 둘이 빠지면 쫓는 중인 작업을
  지웠다 — ROS ④c 4 실행의 정리 4 건이 **모두** 낙찰 1.2–1.8 s 뒤였다 (W-diag B). 지운 로봇이 같은 작업에 입찰 · 주행할 수 있어
  헛걸음 · 확정 거부가 는다 (안전은 그대로). 이제 그 LOCKED 를 처음 본 뒤 `stale_lock_margin_s`(0.5 s) 넘어 만들어진 비컨(stamp)이
  "안 쫓음" 이어야 지운다 (LOCKED 는 보유자의 낙찰 뒤에야 오므로). 옛 코어에서 실패하는 시험 · 변이 M-STAMP 로 고정.

### 10.7 보고서 · P3 와 다르게 한 것

| 보고서 · P3 | b4-wire | 이유 |
|---|---|---|
| BT 가 결정점까지 NavigateToPose 로 서고 AcquireZoneChain (ZoneMoveTo) | 에이전트 경로 게이트 + TrafficGate 의 ZonePathClear (결정점 안이면 goal 취소) | 주행 전에 사슬을 모르고 경로 하나가 사슬 여럿 — §10.1. ZoneMoveTo 는 남겨 두지만 분산 트리는 안 쓴다 |
| task_executor.xml 에 PickupLocked · ZoneMoveTo | 분산 전용 트리 파일 (중앙 트리 바이트 그대로) | "중앙 모드 트리 · 동작은 바뀌지 않게" — 차이 셋을 시험으로 고정해 갈라짐을 막는다 |
| 실패 사유 task_lock_denied | task_lock_failed | 거부와 시간 초과를 함께 덮는다 |
| 에이전트는 fleet_adapter 프로세스의 두 번째 노드 | 로봇 스택(behavior.launch.py)의 별도 프로세스 | 실행기 리매핑과 한곳에서 정하고 에이전트만 재기동 시험 · 장애 분리 |
| 협상 LOCKED 는 사실 (늘 받아들인다) | 신선한 비컨이 "안 쫓고 안 쥠" 이면 지운다 (nego.stale_lock_gc) | 픽업 전 실패한 작업을 아무도 못 잡는 P3 결함 — §10.2 |
| 중앙 hold 는 늘 따른다 | 분산 모드에서는 서버가 살아 있을 때만 | 서버 사망 뒤 latched hold=true 로 영영 서지 않게 |
| 교통 관리자 토큰 + 정족수 | 분산 모드에서 토큰 끔 | 두 권위가 같은 구역을 다른 로봇에 주면 서로 막는다 |
