## 2. 지표 대칭화

도구 `amr_evaluation.slam3d.symmetric` (rclpy 비의존): 모든 행을 같은 SE(2) 지표로 잰다.
**주 열** = 정렬 없는 xy ATE RMSE·최대, SE(2) 정렬 xy ATE RMSE, 정렬 없는 yaw ATE RMSE·최대, 거리 RPE 1·10 m (%), 시간 RTE 10 s —
값은 `se2.ate`·`rpe`·`rte` 그대로 (evaluation.md §4.1). **평가 시간창 = 비교하는 모든 실행 궤적 구간의 교집합.**
**3D 열** (3D 센서 행만, 2D 행은 "해당 없음", 순위에 넣지 않는다) = z |오차| 최대·RMSE, roll·pitch RMSE, |roll|·|pitch| 최대,
지도 바닥 아래(z < −0.05 m) 점 비율, 바닥 대역(z < 0.15 m) 점 z 1 백분위.

s3 표와의 차이 [계산, `/home/CAPYI_AI/runs/b24/b2-offline/sym_old/`]:
- s3 표의 xy ATE 는 **이미 xy 만**이었다 (`tum_to_se2`). 같은 궤적을 새 도구로 각자의 구간에서 재면 s3 표 xy ATE·SE(2)·RPE 가
  표기 자릿수(0.01 cm, 0.01 %)까지 같다 (사전 예측 H0 통과). 리서치 노트 Q4 의 "RTAB-Map 은 xy, LIO-SAM 은 xyz" 비대칭은 표가
  아니라 본문 서술(LIO-SAM xyz 12.8 cm)의 문제였다.
- 공통 창 [4.3, 182.5] s 로 자르면 xy RMSE 변화는 최대 +0.0015 cm (slam_toolbox), 표본 1 786 → 1 783.

  roll·pitch RMSE 0.93° / 0.83°, 바닥 아래 점 3.9 % / 4.2 % — 본문에만 있던 값을 열로).

## 7. 원인 진단

**재생 런치가 SIGINT 를 못 받는 이유** [측정, `tmp/sigtest.sh`·`sigtest2.sh`]: 비대화형 bash 의 `&` 작업은 SIGINT 를 무시(SIG_IGN)한 채
시작하고 이 처분이 exec 로 이어진다 — `ros2 launch` 의 `/proc/<pid>/status` SigIgn 에 SIGINT 비트가 있다. 첫 고침은 처분을 되돌리는
python 래퍼를 **셸 함수**로 감쌌는데, 함수를 `&` 로 부르면 서브셸이 생겨 `$!` 가 서브셸을 가리키고 SIGINT 가 런치에 닿지 않았다
(그 판으로 돈 34 재생 모두 "SIGKILL after 60s"). 배열을 단순 명령으로 실행하도록 고친 판(`2126897`)은 시험 컨테이너에서 SIGINT 1 s 뒤
"user interrupted with ctrl-c" 와 두 노드 "finished cleanly" 로 끝났고, RTAB-Map 마지막 묶음 9 재생에 적용했다 (§6 `launch_exit`).

**RTAB-Map 9.5 / 9.6 s 한 장** [측정]: 원 bag(기록 IMU) 행은 3 회 모두 9.5 s 장을 IMU 대기로 버린다 ("didn't receive IMU newer" 1).
IMU 를 빼거나 공백 없는 IMU 를 주면 9.5 s 는 처리되고 9.6 s 가 빠진다. bag 에서 그 시각에 기록이 멈췄다: `/clock` 은 9.48 에서 멈춘 채
9.5·9.6 s 점군이 기록됐고(`tmp/order.py`), EKF `odom → base_footprint` 는 9.475 → 9.540 사이 0.337 s(벽시계) 끊겼다가 9.540·9.640 이
0.002 s 간격으로 몰려 들어왔다(`tmp/tfgap.py`). 첫 15 s 재생 시험: guess 있음 + `wait_for_transform` 0.2 / 1.0 s → 둘 다 9.6 s 없음,
guess 없음 → 9.6 s 처리 (`tmp/waittest*.sh`). 그래서 원인은 그 장의 휠-EKF guess 조회 실패이고, 기다림을 늘려도 안 풀린다.
정확히 어느 조건에서 조회가 실패하는지(시뮬 시각이 9.48 에 멈춘 동안의 TF 조회 동작)는 확인하지 않았다.
같은 시각 madgwick 공백도 있었다 (§1.2) — 셋 다 route_driver 가 출발한 시각(sim 9.5 s 무렵)이다. 기록 때 CPU 순간 부하로 보인다 (추론).
